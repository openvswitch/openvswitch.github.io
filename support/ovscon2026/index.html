HBN: Hardware-Accelerated DPU Networking with Open vSwitch↑ Top

Emeel Hakin, NVIDIA; Quentin Brrand, NVIDIA; Alin Serdean, NVIDIA

NVIDIA’s Host-Based Networking (HBN) [1]turns the BlueField DPU into a hardware-accelerated router and network-services platform. It combines Cumulus Linux and the FRR BGP daemon to deliver a proven control plane backed by hardware-accelerated packet processing in OVS-DOCA.

At its core, HBN is an OpenFlow controller that translates control-plane events, from BGP updates to configuration changes, into OpenFlow flows and groups. Extensions to Open vSwitch (OVS) make it possible to support switching, routing, VRFs, VXLAN, ECMP, ACLs, and traffic shaping within a single packet-processing pipeline.

HBN can run independently as an underlay router or alongside other OpenFlow controllers, including OVN. By connecting separate OVS bridges, it enables service chaining and lets operators combine HBN with other networking services.

In this talk, we’ll look inside HBN’s architecture, trace how control-plane updates become hardware-accelerated forwarding decisions, and explore the OVS extensions that make it all work. We’ll also share HBN’s scale and performance results, including OpenFlow flow-insertion rates and statistics.

One Tunnel Too Many: No-Overlay Mode in OVN-Kubernetes↑ Top

Riccardo Ravaioli, NVIDIA

Geneve tunnels do a useful job. Sometimes, though, the network already knows the way. On fabrics that already provide an overlay, adding Geneve means sending packets out wearing two coats.

This talk introduces no-overlay mode in OVN-Kubernetes, which lets the cluster default network and primary Layer 3 ClusterUserDefinedNetworks route traffic between nodes using BGP-learned routes, without Geneve encapsulation. OVN continues to provide local networking, network policy enforcement and Kubernetes Services. The choice is per network, so Geneve and no-overlay networks can coexist in the same cluster.

We'll walk through the use cases, follow a packet across nodes, and compare administrator-configured BGP with the managed full-mesh option. We'll also cover the configuration choices that matter: outbound SNAT, MTU and tenant isolation. NVIDIA's DPU-based VM networking provides one concrete example.

The feature is a joint effort between Red Hat and NVIDIA. Attendees will leave with an understanding of how no-overlay mode works, when to use it and which constraints shape deployment.

OVN Network Function Enhancements - VTAP and Active-Active Load Balancing↑ Top

Sragdhara Datta Chaudhuri, Nutanix; Naveen Yerramneni, Nutanix; Aditya Mehakare, Nutanix

This talk covers recent and ongoing work that extends OVN’s network function capabilities with Virtual TAP (VTAP) and active-active load balancing.

VTAP, available in OVN 26.09, enables users to mirror selected traffic to a Virtual Network Function (VNF). Traffic matching a configured access list, along with the corresponding response traffic, is cloned and delivered to the VNF, while the original traffic continues through the normal logical-switch pipeline. This provides a flexible mechanism for use cases such as traffic inspection, network monitoring, intrusion detection, and passive security analysis.

Active-active load balancing is being added for both inline and VTAP mode VNFs. The proposed approach allows traffic to be distributed across multiple healthy VNF members instead of selecting a single member. Flows are consistently mapped to the same VNF instance in both directions, ensuring that request and response traffic are processed by the same service instance. Existing connections remain associated with their original VNF even when the set of active VNF members changes.

Together, these enhancements provide better traffic visibility and improve the scalability of OVN network function.

When using a large public cloud, users do not want to know about or feel the impact of the upgrades of the infrastructure underneath. We have 3 main components:

  1. Our vpc-agent, that programs ovs-vswitchd
  2. ovs-vswitchd
  3. ovs kernel module

In this talk we discuss:

  1. several simple, but clever tricks we use to let restarting vpc-agent syncronize openflow tables and groups into desired state, while current flows allows traffic to continue working, including:
    • using cookies to store "version" to easily clean up flows, that are not actual anymore
    • storing information that must be saved between restarts using openflow note action
    • allocating group IDs
    • thinking about the future when allocating things with limited bits
  2. doing the forbidden: running two ovs-vswitchd in parallel during upgrade (using flow-restore-wait flag):
    • how to make ovs-vswitchd fight each other, and how to make them stop
    • funny things that happen when you forget to create internal port for the bridge
  3. how we do all of this in Kubernetes, which adds its own share of oddities.
    • or nobody guarantees that new container will start in reasonable time

(Un)fortunately, we do not hot-upgrade OVS kernel module. But as a bonus, if you happen to need to and we have time, I have one crazy scheme with loading two OVS modules at once, that might theoretically work.

Bonus #2: what about local services? See the next talk.

Network Security with Address-set synchronisation across Kubernetes Clusters and VMs↑ Top

Sragdhara Datta Chaudhuri, Nutanix; Mansi Sharma, Nutanix

Security policies become difficult to express and enforce when applications span VM networks and Kubernetes workload across multiple clusters. Administrators want to express policy using stable workload identities–such as Kubernetes labels and VM categories–while the data plane must enforce those policies against ever-changing IP address states distributed across independent OVN domains.

In this model, a VPC is a single logical routing, service-discovery, and security-policy domain for workloads distributed across multiple Kubernetes clusters and VM environments, while each environment retains its own control plane. The talk focuses on applying a consistent security policy across this shared VPC even though each control plane has visibility into workloads in its own domain.

OVN Interconnect provides the federation substrate while ACLs keep the enforcement local. A central management service (CMS) creates only high-level, static policy intent: Kubernetes pod and service selectors and VM categories or tags identify the endpoints. Each control plane independently resolves those selectors and VM attributes into local OVN address-sets. Selected local address-sets are then advertised and learned across control planes through OVN Interconnect, preserving local ownership of endpoint discovery and policy enforcement.

The talk concludes with a concrete example of a unified policy matching applications across different Kubernetes clusters and VMs. We show how that policy is implemented using OVN ACLs together with local Address_Sets and learned Address_Sets, and how membership changes propagate without requiring the CMS to manage individual workload IP addresses. This model is well suited to production environments because the security policy remains stable as pods are rescheduled, clusters scale out, or workloads move between nodes—the relevant address sets are updated automatically while the ACL itself remains unchanged.

Teaching AI to Debug OVN: Layer-Aware Troubleshooting with the ovn-kubernetes MCP Server↑ Top

Keshav Kabra, NVIDIA; Surya Seetharaman, Red Hat, LLC.

Diagnosing OVN-Kubernetes incidents means connecting state across many layers: Kubernetes objects, OVN Northbound and Southbound databases, OVS flow tables, and kernel networking. Failed port bindings, broken Geneve tunnels, MTU mismatches and misapplied ACLs often show up only as indirect symptoms. Engineers then have to piece together the cause by hand from logs and CLI output.

This talk introduces the ovn-kubernetes MCP server, a community project that exposes these layers to AI agents as structured, read-only tools. The tools wrap ovn-nbctl, ovn-sbctl, ovn-trace, ovs-ofctl and ovs-appctl, plus Kubernetes and kernel-networking state. The server works on live clusters and also offline, by parsing must-gather and sos-report artifacts. We cover the design choices behind it: wrapper tools instead of generic exec, least-privilege access, and grouping tools by layer. We then show an agent tracing a symptom from a pod to its logical and physical data path to find the root cause.

Attendees will learn practical patterns for exposing OVN/OVS primitives through MCP. They will also see where AI-assisted triage helps and where human checking is still needed.

Route scope delimitation as a control plane scalability mechanism for OVN Interconnect using route tags↑ Top

Lucas Vargas Dias, Magalu Cloud; Julio Cesar Vanti, Magalu Cloud

When VPCs must be peered across availability zones with OVN Interconnect, the obvious way to keep each pair's routes to itself is topological: give every peering its own transit switch, so that route distribution is bounded by who is attached to which L2 domain. The alternative is to put every router on a single shared transit switch and scope route exchange declaratively, with options:ic-route-tag on the advertising side and options:ic-route-learn-tag-rules=allow:<tags> or ic-route-filter-tag on the learning side. The first approach is intuitive and provides isolation in the data plane. It is possible to show that it also produces 2.56x as many Southbound logical flows for identical connectivity, and that this increase results in additional latency on every operation where northd's engine falls back to a full recompute of the lflow node.

The practical conclusion is that route scoping lets an operator buy isolation in the control plane instead of in the topology, and that doing so is substantially cheaper - not only in memory, but in the latency of every unrelated northbound write, in flow-installation time after a reconnect, and in the cost of the full recomputes. The trade-off must be stated plainly: on a shared transit switch, tag-based scoping constrains route learning only. The VPCs share one L2 domain, so a manually configured static route can still reach across it. Where isolation must hold in the data plane, the per-pair topology remains necessary, and our measurements quantify what that guarantee costs.

A Switch, a Load Balancer, and an ACL Walk into a Pipeline…. And Conntrack Ruins Everything↑ Top

Surya Seetharaman, Red Hat, LLC.; Nadia Pinaeva, NVIDIA

User Defined Networks (UDNs) in OVN-Kubernetes provide strong tenant isolation — each UDN is an independent OVN topology island. However, isolation is not always the end state: address space exhaustion, inter-team service access, and platform migrations all require controlled connectivity between these islands.

ClusterNetworkConnect (CNC) is a new admin API added in OVN-Kubernetes v1.3 that declaratively connects isolated UDNs — with full pod-to-pod connectivity, service-only access, or both. Connectivity is symmetric but non-transitive.

This talk covers the design in three parts. First, the OVN topology: a distributed transit router is peered with each connected network's router using point-to-point subnets carved deterministically from a user-configured CIDR. Second, services across networks: load balancers are added to the switches of connected networks so cross-network DNAT works with the existing routing. Third, an ACL puzzle: you can easily allow service traffic while dropping direct pod-to-pod with a pass action, right? Join our talk to see how interaction between load balancers on switches, conntrack, and ACL evaluation order has other ideas. We walk through what breaks, the workaround we shipped, and why finding the long-term fix isn't easy.

One Shared Gateway, a Thousand Routers: Scaling ARP/NDP in OVN-Kubernetes↑ Top

Jaime Caamano, Red Hat, LLC.; Matteo Dallaglio, Red Hat, LLC.; Tim Rozet, NVIDIA

This talk tells the story of an ARP and NDP scaling problem uncovered while scaling user-defined networks in OVN-Kubernetes. A cluster may have hundreds or thousands of user-defined networks, each with its own gateway router, while those routers share the same physical uplink, IP address, and MAC address.

On the shared gateway bridge, OVN-Kubernetes must deliver neighbor-discovery traffic between the physical network and many logical-router patch ports. These packets do not carry enough context to identify the originating user-defined network. In particular, an ARP reply cannot be tracked with conntrack and mapped back to the router that sent the request. The historically safe option has therefore been to fan the traffic out to every relevant patch port. At scale, a single reply can pass through several router pipelines, duplicate learned neighbor states, expand the OpenFlow footprint, and eventually exceed OVS recirculation limits.

We will trace how this behavior surfaced at scale, the constraints that any solution must preserve, and the approaches explored in OVN-Kubernetes to reduce fan-out without changing neighbor-resolution semantics. We will cover the short-term flow fix that constrains ARP/NDP fan-out on the shared gateway bridge, and the mid-term prototype that steers discovery through the default gateway router and propagates the learned bindings to the user-defined networks.

Finally, we will present OVN’s Shared MAC-binding scopes. Related logical router ports can use a common set of learned neighbor bindings, avoiding per-router duplication. This allows OVN-Kubernetes to learn through a single gateway router and steer ARP/NDP traffic to it instead of fanning that traffic out to every gateway router.

Join us to trace an ARP storm from the OpenFlow tables where it started to an emerging OVN feature, shaped by the OVN and OVN-Kubernetes communities working together to solve it at the right layer.

A Unified Networking Fabric for VMs and Multi-Cluster Kubernetes workloads↑ Top

Sragdhara Datta Chaudhuri, Nutanix; Priyankar Jain, Nutanix

Hybrid applications increasingly span virtual machines and workloads distributed across multiple Kubernetes clusters. This talk presents Nutanix’s experience building Flow CNI, a networking architecture based on OVN-Kubernetes and OVN-IC. It extends the VPC networking model across these environments, enabling VM and Kubernetes networks to participate in a common logical routing domain with federated service reachability while preserving the independent control-plane boundaries of each environment. The resulting fabric supports two related use cases: connecting VMs and Kubernetes pods within a shared VPC, and extending that VPC across multiple Kubernetes clusters.

The architecture uses OVN connectivity hierarchically. Within a Kubernetes cluster, OVN-Kubernetes Interconnect mode distributes OVN control and datapath state across zones with local OVN databases. Across clusters – and between Kubernetes and the VM networks – OVN Interconnect links these independent OVN domains through transit switches and a shared interconnect database. The result is an “interconnect of interconnects”: each environment remains locally managed, while the VPC presents a unified logical network to the user. We will discuss the targeted enhancements made in OVN and OVN-kubernetes to achieve this model.

Service reachability is bi-directional: OVN-IC advertises VM-side load balancer VIPs to Kubernetes and Kubernetes ClusterIP services to the VM domain. Each side forwards traffic across the OVN-IC transit path, while backend selection remains local to the destination domain.

The presentation also explains cross-cluster DNS for ClusterIP services. A controller publishes service FQDNs, ClusterIPs, and VPC visibility to a shared OVSDB database, while a CoreDNS extension builds per-VPC views using the standard svc.cluster.local naming model.

Attendees will leave with a practical model for building a unified networking fabric across VMs and multi-cluster kubernetes. The model federates independent OVN domains, exchanges routes and VIPs, and preserves local control-plane ownership while presenting a single VPC to users.

Same Flow, Same Path: Software/Hardware Hash Alignment↑ Top

Eli Britstein, NVIDIA

In this brief talk, I will cover a long-standing hardware-offload problem in OVS: software and hardware can compute different values for the UDP tunnel source port (VXLAN, Geneve) and for dp_hash used in select-group load balancing. This happens whenever a flow is handled by both paths — the first packet of a flow is by definition processed in software before the flow gets offloaded, and later packets take the hardware path, and similarly when flows are only partially offloaded. The result is inconsistent ECMP, asymmetric traffic, and steering that can fail to converge. I'll briefly recount the history, including why earlier attempts to solve this in the kernel datapath never went through, and show how the userspace datapath, the dpif-offload provider framework, and DOCA offload finally make a clean solution possible via optional provider callbacks. The patches were implemented by Eelco Chaudron.

Two OVN-Kubernetes, One DPU↑ Top

Alin Serdean, NVIDIA; Igal Tsoiref, Red Hat, LLC.

A DPU runs its own OS and its own Kubernetes node. Today ovn-kubernetes runs in DPU mode on the card and DPU-host mode on the host, both serving the host cluster, so pods scheduled on the DPU itself get nothing. That needs a second, full-mode instance on the same card.

Each instance keeps its own OVN databases and its own Kubernetes API. Only what's actually shared gets split up. OVN has co-hosted ovn-controller since 23.03, and 26.09.0 drops the experimental tag.

The hard parts:

  • system-id is the one key that can't be made chassis-specific
  • conntrack zones have to stay clear of the shared gateway zones
  • management port names run out of room at 15 characters
  • two instances can't share a gateway bridge, since ovnk owns its whole flow table
  • bridges, nftables tables, metrics ports and socket paths all need an owner

We'll walk the proposal and demo the prototype.

Rebuilding an OpenFlow Controller in Rust↑ Top

Or Mazza, NVIDIA; Quentin Barrand, NVIDIA; Alin Serdean, NVIDIA

HBN turns a BlueField DPU into a hardware-accelerated switching and routing platform. Its controller translates routing, switching, security, and NAT configuration into OpenFlow rules for Open vSwitch.

We rewrote this controller from C to Rust while preserving binary compatibility. Our goals were better memory safety, concurrency, and testability, along with easier maintenance. The rewrite also delivered measurable performance gains: insertion rates increased by 8%, deletion rates by 14%, and flow statistics collection became 57% faster.

In this talk, we’ll explore why we chose Rust, how we introduced it without disrupting users, and practical lessons learned from running HBN in a real DPU networking platform.

We would also like to open the debate on implementing parts of OVS in Rust. We’ll discuss where it might fit, what bindings to existing C code would be required, and whether the benefits we saw in HBN could carry over to OVS.

One API to Rule Them All: Reworking the OVS Hardware Offload Layers↑ Top

Eelco Chaudron, Red Hat, LLC.

Open vSwitch (OVS) historically supported hardware offload through implementations tightly coupled to the dpif-provider layer. While this approach worked, it led to a rigid model where each provider integrated offload capabilities in its own way, making it harder to extend and share functionality across vendors.

OVS supported multiple backends for offload: the kernel datapath leveraged the TC flower classifier, while the userspace datapath integrated with DPDK using rte_flow. Both paths exposed their functionality through the netdev-offload APIs, but the design resulted in duplicated logic and limited opportunities for consistency and reuse. Vendor-specific capabilities had to be reimplemented in each provider, and adding new offload features required invasive changes in multiple places.

This talk presents the new dpif-offload API layer that has since landed in OVS. It provides a unified and more flexible abstraction for hardware offload that sits above the provider-specific implementations. By centralizing offload handling, we have simplified vendor integration, reduced duplication, and enabled more extensible offload pipelines. We will walk through the architecture, cover the migration from the old netdev-offload model, and look at what this foundation enables going forward.

Conntrack: Semantics and Scale↑ Top

Aaron Conole, Red Hat, LLC.

Conntrack was introduced to Open vSwitch in 2014 and 2015 to provide stateful flow processing, grouping related packets together and as a result, reducing the amount of flows in the flow table through this grouping. However, it has evolved over the years into a way to provide a useful L3/L4 interface into the OpenFlow pipeline.

In this talk we'll explore the questions that are currently being asked of conntrack:

  • What behaviors need to be common across all conntrack implementations?
  • How can the userspace implementation scale to meet the modern demands placed on it?
  • How can it work with hardware to extend the ct() interface through an acceleration path?

In this talk, we'll look at how conntrack has changed over the last decade, and the ongoing work to answer the above questions. We'll look at what work has been done, and what remains to be merged upstream, and we'll show how others can get involved.

Stateless Load Balancing in OVN↑ Top

Alexandra Rukomoinikova, K2 Cloud

Stateless load balancing in OVN is not a new idea: the use_stateless_nat option already exists, but its limitations (reply traffic is SNATed 1:1 to the VIP, so a backend cannot serve more than one VIP) kept it from solving the real problem - conntrack state on the gateway chassis pins every connection to one node and prevents gateways from scaling horizontally.

This talk is the story of how we got from there to the new "deferred-nat" load balancer option: the approaches we considered (conntrack synchronization, extending use_stateless_nat, cross-AZ backends, moving the NAT off the gateway) and why we settled on the last one. The backend is selected statelessly per packet on the router, the packet is delivered to it by MAC, and the DNAT and conntrack state are created on the backend's own hypervisor. To keep established sessions alive when backends change, select groups are updated incrementally instead of being rebuilt. Finally, how we use this in production and what is left to do.

Targeted Megaflow Revalidation in Open vSwitch↑ Top

Gaetan Rivet, NVIDIA

Open vSwitch revalidators keep datapath megaflows consistent with the OpenFlow tables and the switch state. Periodic revalidation is inexpensive, as xcache allows statistics to be updated without retranslation. After a configuration change, however, all megaflows are translated again, whether or not the change can affect them.

In large deployments, this cost adds to the pressure on flow-capacity control and can lead to the eviction of useful datapath flows. In some cases, this added pressure can destabilize the revalidators and lead to a megaflow population collapse. The cache must then be rebuilt while the system is already overloaded. This problem has limited the scale of our Open vSwitch deployments at NVIDIA.

This talk presents targeted megaflow revalidation, a feature implemented in the OVS-DOCA fork. It records the reasons for each revalidation and extends xcache to track the dependencies of each megaflow, so that only the megaflows affected by a change are translated again.

We will explain the design and the challenge of tracking megaflow dependencies completely, including indirect and negative dependencies such as watched ports and missing groups. We will describe how AI-assisted testing helped cover the dependency matrix.

Furthermore, this feature gives controller developers a way to structure their OpenFlow pipeline to bound the impact of changes to its configuration.

Finally, we will place this work in the wider effort to stabilize revalidation. We intend to propose the existing implementation upstream, while work continues on an improved control law for the remaining flow-capacity instability.
